# Plan: Morphing `hms-webb` into a Real Frontend Module

**Status:** Planning — nothing below has been implemented
**Design reference:** [architecture/future/POM_STRUCTURE.md](../../architecture/future/POM_STRUCTURE.md)
**Branch:** `architecture/gsn-creating-a-new-pom-structure`

This is the step-by-step breakdown for turning `hms-webb` from an empty
`packaging: pom` container into a running Spring Boot module that serves
the Angular build directly, per the target design. Each phase is a
checkpoint — nothing here should be done in one uninterrupted pass without
confirming along the way.

---

## Phase 1 — Scaffold the Spring Boot module

- [ ] `hms-webb/pom.xml`: `packaging: pom` → `packaging: jar`
- [ ] Add `spring-boot-starter-webmvc` (matches the starter name already
      used in `hms-jar` for this Spring Boot 4.x setup) + `spring-boot-devtools`
      (runtime, optional)
- [ ] Add `spring-boot-maven-plugin` to `<build><plugins>`
- [ ] Add main class `com.hms.webb.HmsWebbApplication`
- [ ] Add `src/main/resources/application.properties` — needs at minimum
      `spring.application.name` and `server.port` (see Phase 4, port isn't
      finalized yet)
- [ ] Verify `mvn -pl hms-webb spring-boot:run` boots cleanly with no
      static content yet (should just be an empty Whitelabel error page —
      that's expected before Phase 2)

## Phase 2 — Wire Angular's build output directly into `static/`

- [ ] `hms-webb/angular/angular.json` → `architect.build.options.outputPath`:
  ```jsonc
  "outputPath": {
    "base": "../src/main/resources/static",
    "browser": ""
  }
  ```
- [ ] Run `ng build` from `hms-webb/angular/` and confirm `index.html` lands
      at `hms-webb/src/main/resources/static/index.html` (root level, **not**
      nested under a `browser/` subfolder)
- [ ] Restart `hms-webb` and confirm the built Angular app loads at
      `http://localhost:<webb-port>/`
- [ ] Confirm client-side routing works on a hard refresh of a non-root
      route (Angular's router needs a fallback to `index.html` for deep
      links — Spring Boot's default static handler does **not** do this
      automatically; likely needs an error-page/forward rule. Flag as a
      decision point if it doesn't work out of the box.)

## Phase 3 — Retire the stale manual copy in `hms-jar`

- [ ] Confirm (don't assume) whether anything currently depends on
      `hms-jar/src/main/resources/static/*` being served from the backend
      — **this content is currently git-tracked**, not gitignored, so it
      was committed on purpose at some point. Ask before deleting.
- [ ] Once `hms-webb` is confirmed serving correctly, remove the static
      files from `hms-jar` and add `hms-jar/src/main/resources/static/*`
      (or the specific committed files) to version-control cleanup.
- [ ] Add `hms-webb/src/main/resources/static/` to `.gitignore` (it's
      generated by `ng build`, same treatment as `hms-webb/angular/dist/`
      already gets) — decide whether *any* placeholder (e.g. `.gitkeep`)
      is needed so the empty dir exists pre-build.

## Phase 4 — Cross-cutting config decisions (need answers, not just code)

- [ ] **Port for `hms-webb`.** Proposed `8082` in the design doc — not
      confirmed.
- [ ] **CORS.** Backend controllers are currently *inconsistent* already,
      independent of this migration:
      - `AppointmentController`, `UserController`: `@CrossOrigin(origins = "http://localhost:4200")`
      - `ConsultationController`: `@CrossOrigin(origins = "*")`
      - `BillingController`: custom config, needs checking
      Once `hms-webb` serves the built app on its own origin, decide:
      same-origin via reverse proxy (no CORS needed) vs. keeping CORS and
      adding the new origin everywhere consistently. This is a good moment
      to also fix the pre-existing `*` vs fixed-origin inconsistency, not
      just bolt on a third origin.
- [ ] **Dev workflow clarity.** `ng serve` (port 4200, fast reload) remains
      the loop for active frontend development; `hms-webb` is the
      packaged/production-like serving path. Document this explicitly so
      nobody expects hot-reload from `hms-webb` itself.

## Phase 5 — Documentation catch-up

- [ ] Once Phases 1–4 are actually done and verified working, promote
      `architecture/future/POM_STRUCTURE.md` → merge its content into
      `architecture/old/` (it stops being a future proposal and becomes a
      description of the current system) and update its "Status" line.
- [ ] Update root `README.md` Quick Start / Project Structure if the
      dev-run instructions change (e.g. two ways to run the frontend).
- [ ] Update `architecture/old/ARCHITECTURE.md` and `COMPONENTS.md` counts
      if this introduces new modules/services worth tracking.

---

## Explicitly out of scope for this plan

- Any change to `hms-jar`'s business logic, entities, or API contracts.
- Deployment/CI wiring (this plan only covers getting the two modules
  correct locally).
